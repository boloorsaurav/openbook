The interactive components

Widgets

A widget is a self-contained interactive piece — sliders, click handlers, drag interactions, number inputs — that helps a student feel a mathematical idea instead of just reading about it. Openbook has around 33 widgets, all following the same pattern.

The pattern

Every widget follows four rules. If a new widget violates one of them, fix the widget — not the rules.

  1. It's a single React component that owns its own state via useState.
  2. It wraps itself in <WidgetShell label="..." badge="..." /> — the page never adds the shell.
  3. All colours come from CSS variables (var(--accent), var(--green), etc.). No hardcoded hex values.
  4. It's genuinely interactive — sliders, buttons, inputs that change something visible. Not a static SVG masquerading as a widget.

Three case studies

Three widgets worth understanding in more depth — each illustrates a different implementation pattern.

VennDiagramExplorer — toggling SVG regions

Inside Chapter 1 (Sets). The widget renders two overlapping circles as inline SVG. The trick: each of the four regions (A only, B only, intersection, neither) is its own SVG path. When the user picks an operation from a row of buttons, the component flips an opacity/fill property on each region. No external library — just React state controlling SVG attributes.

ConicGallery — parametric curves with four modes

In Chapter 10. One widget handles all four conics (circle, parabola, ellipse, hyperbola) by generating sample points from a parametric formula and stitching them into an SVG path. When the user clicks "hyperbola", the widget swaps the formula and re-renders. Foci and directrix are computed from a, b, c and drawn as separate markers. About 220 lines for all four conics together.

LimitExplorer — the numeric-table approach

In Chapter 12. Instead of a visualization, this widget uses a table — it picks four decreasing values of h and shows f(a − h) and f(a + h) side by side. When the two columns converge, the limit exists. When they don't, it doesn't. The interaction is just clicking between sample functions. Sometimes a table tells a story better than a chart.

When to add a new widget vs reuse

Reuse if:

  • The existing widget does the same thing with different parameters (e.g., a different function on FunctionGraphExplorer).
  • You'd be duplicating >50% of an existing widget's code.

Build new if:

  • The concept needs a fundamentally different interaction (drag vs slider vs click).
  • You'd need to bend the existing widget out of shape to fit the new use.
  • The new chapter has a unique visual metaphor (Pascal's triangle, the Argand plane, a 52-card grid).
Deep diveThe component-defined-inside-parent bug

A common React mistake is defining a sub-component inside a parent component's render function. Every parent re-render creates a new function reference, which React treats as a different component — so it unmounts the old one, remounts the new one, and input focus is lost.

This bit us once in RatioEquivalenceChecker: a small Field sub-component was defined inside the parent. Typing "30" would render "3", then the remount would steal focus before the "0" could land. The fix: hoist the sub-component to module scope. Always define helpers outside the parent.

Deep diveThe Quiz widget — used by every chapter

Quiz takes a pool prop (typed array of QuizQuestion) and a count prop (defaults to 10). It samples count questions randomly from the pool, walks the user through them with hint-on-demand, marks correct/ wrong with green/red, shows the explanation, and ends with a score screen. The pool itself lives in src/data/<slug>-questions.ts — quiz questions are data, not UI.
