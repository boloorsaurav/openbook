How the pieces fit

Architecture

The whole codebase is organised in three layers. Once you internalise these layers, every file in the repo has a clear home.

The three layers

Think of it like an onion — the page on the outside, layout in the middle, widgets in the centre.

Each layer composes the ones below it.

1. Layout layer · src/components/layout/

The chrome that wraps every page — the parts that look the same no matter which chapter you're on.

  • Navbar — sticky top bar with the "Openbook" brand and the current chapter's title.
  • Sidebar — left rail listing every chapter in the current grade. Highlights the active one.
  • CalloutCard — the soft-coloured box used to highlight a key idea or definition inside the prose.
  • WidgetShell — the rounded card with a header bar that every widget wraps itself in.

2. Widget layer · src/components/widgets/

The interactive pieces. Each widget is a self-contained React component with its own state — a slider, a click handler, a number input, whatever the concept needs. Around 33 widgets total across all chapters. See the widgets page for the full catalogue.

3. Page layer · src/app/…/page.tsx

Each chapter is one TypeScript file. It imports the layout pieces, imports the widgets it needs, and writes the prose inline. There is no template engine — the page IS the chapter. That keeps every chapter independently editable.

The shape of a typical chapter page

Every chapter page is built from the same six ingredients: a header block (title + metadata pills), several numbered sections, callout cards inside sections, widgets dropped in where they help, a quiz at the end, and a footer with "Chapter N of M". Once you've read one chapter page, you can navigate any of them.

How a request flows

The site is statically exported, so the "request" story is unusually short. There is no server doing per-request work. 

1. You visit openbook-ncert.vercel.app/read/grade-11/ch5
2. Vercel serves the pre-built /read/grade-11/ch5/index.html
3. Browser loads the HTML, then small JS bundles for any client-side widgets
4. Widgets hydrate (React attaches event listeners) and become interactive

Building the site (locally npm run build, or automatically on every git push) runs Next.js once. It walks every route, renders each one to HTML, and writes them to disk. Vercel uploads the result.

Data flow

"Data" in Openbook is a much smaller story than in a typical app. There's no database. There are only two flavours of data, and both are TypeScript or Markdown files that live in src/data/.

  • src/data/grade-11-chN-questions.ts — the quiz pool for chapter N. Each file exports a typed array of QuizQuestion objects.
  • src/data/briefs/ — the DeepSeek-generated source briefs (Markdown). Read once during chapter authoring, never at runtime.
Deep diveWhy one file per chapter, not a template?

A template would force every chapter to look the same, and force template changes to ripple through every chapter at once. With one file per chapter:

  • Each chapter can deviate when it needs to (more sections, custom prose, a one-off layout) without ceremony.
  • Edits are contained — if you tweak the prose in Ch5, nothing else is at risk.
  • When you ask Claude to build a new chapter, it copies the structure of an existing one but writes everything fresh — the consistency comes from convention, not enforcement.

The trade-off is that updating shared structure (say, the metadata pill style) means touching every chapter file. With ~21 chapters that's still cheap.

Deep diveSidebar drift — and why it's annoying

Every chapter's page.tsx contains its own CHAPTERS array — a hardcoded list of all chapters in that grade. When you ship a new chapter, you have to update that array in every previously-shipped chapter to mark the new one as available.

The create-chapter skill does this automatically (with a sed command), but it's a manual chore if you ever bypass the skill. A future cleanup could hoist the array into a single shared file — for now, it duplicates by design to keep each chapter standalone.
