The visual language

Design System

Two fonts, three semantic colour roles, a handful of border and surface tokens. Once you know the system, the whole site looks "like Openbook" without any per-page styling effort.

Fonts

Two fonts are loaded globally in src/app/layout.tsx via next/font/google:

CSS variableFontWhere it's used
--font-displayOutfit (400–900)All headings (h1–h6), section numbers, the brand name, button labels.
--font-bodyInter (400–700)Everything else — body prose, UI labels, callouts.

The split is enforced in globals.css — every heading tag automatically gets Outfit with negative letter-spacing. You don't have to think about which font to apply.

Color tokens

All colours come from CSS variables defined at the top of globals.css. There are four families: an accent family (near-black, used for UI chrome), and three semantic families (green, yellow, red) used for what they typically mean.

The one rule that explains why both --accent and --green exist

Accent is for UI chrome. Buttons, sidebar borders, the brand wordmark, the active-tab indicator — anything that's neutral, structural, "part of the app". Green is semantic. A correct quiz answer, a successfully solved equation, a toggle in the "on" state.

Never use --accent where you mean "correct" — that's a job for --green. And never use --green for plain UI like "the submit button" — that's a job for --accent.

Buttons

Two button styles, both defined globally in globals.css. Use them by adding a class to your <button> — no extra styling needed.

Both buttons use Outfit Bold at 13px and have a small downward translate on :active to give them a satisfying "press".

WidgetShell anatomy

Every interactive widget wraps itself in <WidgetShell> for visual consistency. The shell provides three slots: a header label, an optional right-aligned badge, and the body.

WidgetShell — the standard wrapper for every interactive widget.

All widgets wrap themselves in WidgetShell. That means a page never has to add a shell — you just drop in <CountingPrinciple /> and the framing comes along for the ride.

Section numbering

Inside chapter pages, each major section starts with a giant Outfit-900 number, a tiny eyebrow label, and an h2 title. The pattern is the same every time, so readers learn it once and can skim any chapter at the same speed.

Deep diveWhy CSS variables instead of Tailwind config?

Tailwind v4 reads CSS variables natively at runtime, which means tokens can live in one place (globals.css) and be used both inside Tailwind classes and inside inline style attributes. That uniformity matters for widgets, which use a mix of both. Putting tokens in tailwind.config would limit them to Tailwind classes only.

Deep diveNever hardcode a hex value

Inside any component, colours should be referenced as var(--accent) or via a Tailwind class that maps to one. Hardcoded hex values break the system: if the palette is ever tuned, the hardcoded values won't follow. The skill explicitly checks for this when building a new chapter.
