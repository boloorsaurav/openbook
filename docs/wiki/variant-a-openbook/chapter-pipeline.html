From PDF to shipped chapter

Chapter Pipeline

Building a new chapter from scratch would take Claude a long, expensive read of the source PDF. The pipeline solves that by splitting the work in two: a cheap model extracts a clean brief, then Claude builds the page from the brief. The result is ~100× cheaper than reading the PDF directly.

The big idea

Two stages, three artefacts.

A typical chapter build runs in about 90 seconds and costs roughly two cents. Without the pipeline, Claude would consume the entire PDF as input — burning through tokens for the exercise problems and answer keys you'll throw away anyway.

Stage 1 — DeepSeek extracts the brief

The shell script .claude/skills/create-chapter/scripts/make-brief.sh does the whole thing:

  1. Runs pdftotext to convert the PDF to plain text.
  2. Reads the strict prompt from brief-prompt.txt.
  3. Posts the prompt + chapter text to the DeepSeek chat API.
  4. Saves the response to src/data/briefs/<slug>-brief.md.

Why DeepSeek and not Claude here?

DeepSeek's API is dramatically cheaper for input-heavy summarization tasks. A typical NCERT chapter is 5,000–13,000 words; DeepSeek charges fractions of a cent to read it. Claude would do this fine but cost 100× more.

What's in the brief

The prompt is strict — DeepSeek must follow this output schema:

  • A YAML frontmatter block with chapter number, title, route, read time.
  • One numbered section block per major topic, each containing: concepts (every rule, definition, and pattern), worked examples (only where the source walks through a solution), callout cards (1–3 key insights), widget idea, key terms.
  • Exactly 25 quiz questions as a JSON array with question, options, answer (0-indexed), hint, explanation.

What's stripped out

The prompt explicitly tells DeepSeek to remove all exercise blocks — "Try these", "Figure it out", end-of-chapter problems. Those are valuable in a textbook but they're not what the brief is for. We want the teaching, not the homework.

Where the API key lives

The DeepSeek key is in .env.local at the repo root. That file is gitignored — it never reaches GitHub. The script also reads DEEPSEEK_API_KEY from your shell env if you've set it that way.

Stage 2 — Claude builds the page

Once the brief exists, Claude does five things in order:

  1. Reads the brief only — never the original PDF. The brief is now the source of truth.
  2. Extracts the quiz JSON from the brief and writes it as a typed TypeScript file at src/data/<slug>-questions.ts.
  3. Builds new widgets for each widget idea in the brief, reusing existing ones if a fit is obvious.
  4. Writes page.tsx, copying the structure of an existing chapter and filling in fresh prose from the brief.
  5. Syncs sidebars in every previously-shipped chapter so they link to the new one.

Then npm run build is run to confirm everything compiles, and a git branch + PR is opened with the changes.

How to invoke the skill

Type either of these into the Claude chat:

create chapter 3 for class 11
build Grade 11 Chapter 3 using the create-chapter skill

The skill lives at .claude/skills/create-chapter/SKILL.md and Claude reads it automatically. No magic invocation needed.

Deep diveThe max_tokens evolution

DeepSeek's output is capped by max_tokens in the API request. We started at 6,000 (works for ~70% of chapters), bumped to 8,000 after Ch2 truncated mid-quiz, then to 10,000 after Ch12 (the long Limits & Derivatives chapter) truncated again. The current value is in make-brief.sh line 89.

The signal that you need to bump it: the JSON quiz array at the end of the brief is missing its closing ]. jq will refuse to parse and the script fails fast.

Deep diveThe two-stage cost model in plain English

LLM pricing is mostly about input tokens. A chapter PDF turned into text is ~50K tokens of input. If Claude reads that, you pay for all 50K — even though only ~20% of it (the teaching content) is what you need. DeepSeek is the "cheap reader" that summarises 50K → 3K. Claude then reads the 3K and writes the page. Total input to Claude drops by ~94%.

It's the same trick that made the "extract then act" pattern a staple of LLM-powered tools: use a cheap model to compress noisy input, use the expensive model to do the part that needs intelligence.
