Welcome

Openbook, end to end

Openbook is a static Next.js site that turns NCERT chapters into interactive learning pages. This wiki is the manual to its codebase.

The 30-second version

Openbook turns textbook chapters into web pages you can actually play with. Each chapter is one big file that mixes prose, callout boxes (the highlighted tips), and interactive widgets (sliders, drag-and-drop, calculators). A quiz at the end checks understanding. The site has no backend — every page is pre-built, so it loads instantly and costs nothing to run.

Each chapter is one page.tsx file (Next.js App Router, static export) that imports layout primitives, drops in widgets where helpful, and ends with the Quiz widget fed from a typed pool in src/data/. The build pre-renders every route to plain HTML. New chapters are authored via a 2-stage pipeline: DeepSeek summarises the PDF into a structured Markdown brief, then Claude consumes the brief to generate the page, widgets, and quiz pool.

How the pieces fit

Architecture

The whole codebase organises into three layers. Once you internalise these layers, every file in the repo has a clear home.

The three layers

Think of it like an onion. The page is what someone sees in their browser. The layout pieces are the chrome around every page — the top bar, the left sidebar, the little highlighted boxes. The widgets are the interactive bits in the middle, like a slider that demonstrates how the slope of a line works.

Three concentric layers. Page-level files (src/app/.../page.tsx) at the top compose layout primitives and widgets. Layout primitives (src/components/layout/) provide shared chrome. Widgets (src/components/widgets/) are self-contained interactive components owning their state via useState. Strict separation: layout never imports widgets, widgets never import layout primitives other than WidgetShell.

Each layer composes the ones below it.

1. Layout layer · src/components/layout/

The chrome that wraps every page — the parts that look the same no matter which chapter you're on.

  • Navbar — sticky top bar with the brand and the current chapter's title.
  • Sidebar — left rail listing every chapter in the current grade.
  • CalloutCard — soft-coloured box for key ideas inside the prose.
  • WidgetShell — the rounded card every widget wraps itself in.

2. Widget layer · src/components/widgets/

The interactive pieces. Each widget is a self-contained React component with its own state. See the Widgets section below for the full catalogue of ~33 widgets.

3. Page layer · src/app/…/page.tsx

Each chapter is one TypeScript file that imports layout pieces, imports widgets, and writes the prose inline. No template engine — the page IS the chapter.

The shape of a typical chapter page. Every chapter is built from the same six ingredients: header block (title + metadata pills), numbered sections, callout cards inside sections, widgets dropped in where they help, a quiz at the end, and a footer with "Chapter N of M".

How a request flows

There's no server doing work behind the scenes — every page is pre-built when the site is deployed. Visiting a chapter is just a static file download, then the interactive widgets "wake up" in your browser.

Static export means there's no server-side runtime. Vercel serves the pre-rendered HTML, Next.js's client runtime hydrates the page in the browser, and any client components (every chapter, because of "use client";) attach their event listeners. 

1. You visit openbook-ncert.vercel.app/read/grade-11/ch5
2. Vercel serves the pre-built /read/grade-11/ch5/index.html
3. Browser loads HTML, then small JS bundles for client-side widgets
4. Widgets hydrate (React attaches event listeners) and become interactive

Data flow

Data in Openbook is a small story. No database. Only two flavours, both as files in src/data/:

  • src/data/grade-11-chN-questions.ts — the quiz pool for chapter N. A typed array of QuizQuestion objects.
  • src/data/briefs/ — DeepSeek-generated source briefs (Markdown). Read once during authoring, never at runtime.
For PMs To edit a chapter's quiz: open the matching chN-questions.ts file. It's just a list of question objects. Add, remove, or edit them by hand.
For engineers Quiz pools are bundled into the static page at build time. There's no runtime data fetch and no separate JSON file — the array literal becomes part of the page's JS bundle. To change question content, edit the TS file and rebuild.
Why one file per chapter, not a template? Each chapter can deviate when it needs to without ceremony. Edits are contained. The shared structure is enforced by convention, not by code. The trade-off: updating shared structure means touching every chapter file (~21 of them, still cheap).
Sidebar drift. Each chapter's page.tsx contains its own CHAPTERS array — a hardcoded list of all chapters in that grade. When you ship a new chapter, you have to update that array in every previously-shipped chapter. The create-chapter skill does this with a sed command. A future cleanup could hoist the array into one shared file.

The visual language

Design System

Two fonts, three semantic color roles, a handful of surface and border tokens. Once you know the system, the whole site looks consistent without per-page effort.

Fonts

Two fonts power the whole site. Outfit is used for headings — it has that clean modern feel. Inter is used for body text — it's optimised for screen reading. You don't have to pick which font to use anywhere; the system picks for you based on where text appears.

Loaded globally in src/app/layout.tsx via next/font/google. Bound to CSS variables --font-display (Outfit, weights 400–900) and --font-body (Inter, 400–700). A global rule in globals.css applies Outfit to all h1–h6 tags automatically with letter-spacing: -0.02em.

VariableFontUsed for
--font-displayOutfitAll headings (h1–h6), section numbers, brand, button labels.
--font-bodyInterBody prose, UI labels, callouts.

The one rule that explains why both --accent and --green exist. Accent is for UI chrome — buttons, borders, brand. Green is semantic — correct quiz answers, "on" toggle states, successful outcomes. Don't use accent where you mean "correct"; don't use green for plain UI.

WidgetShell anatomy

Every interactive widget wraps itself in <WidgetShell>. The shell provides three slots: header label, optional right-aligned badge, body.

WidgetShell — the standard wrapper for every widget.

All widgets wrap themselves. A page never adds a shell — you render <CountingPrinciple /> and the framing comes along for free.

For engineers WidgetShell.tsx is ~45 lines. Accepts label, optional badge, and children. Renders the header bar with bg-sidebar background and the body with p-5. Read it once and you've understood every widget's outer layout.

Section numbering inside chapters

Each section starts with a giant Outfit-900 number, a tiny eyebrow label, and an h2 title. Same shape every time — readers learn it once and skim any chapter at the same speed.

Why CSS variables instead of Tailwind config? Tailwind v4 reads CSS variables natively. Tokens defined in globals.css work both inside Tailwind classes and inside inline style attributes. Putting them in tailwind.config would limit them to Tailwind class usage only.

The interactive components

Widgets

A widget is a self-contained interactive piece — sliders, click handlers, drag, number inputs — that helps a student feel an idea instead of just reading about it. Openbook has around 33 widgets, all following the same pattern.

The pattern

Every widget follows the same recipe: it owns its own state (whatever the user is currently interacting with), wraps itself in a standard card frame (so all widgets look like siblings), pulls its colours from the shared design system, and actually does something — moves, changes, calculates — when the user interacts with it. No static SVG pretending to be a widget.

Four rules. Violations are bugs.

  1. One React component, owns its state via useState.
  2. Wraps itself in <WidgetShell label="..." badge="...">.
  3. Colors via CSS variables only. No hardcoded hex.
  4. Genuinely interactive — visible state changes on user input.

Three case studies

VennDiagramExplorer — toggling SVG regions

Chapter 1 (Sets). Two overlapping circles in inline SVG. Each of the four regions (A only, B only, intersection, neither) is its own SVG path. When the user picks an operation, the component flips opacity/fill on each region. No external library — just React state controlling SVG attributes.

ConicGallery — parametric curves with four modes

Chapter 10. One widget handles all four conics by generating sample points from a parametric formula and stitching them into an SVG path. Foci and directrix are computed from a, b, c and drawn as separate markers. About 220 lines for all four conics together.

LimitExplorer — the numeric-table approach

Chapter 12. Instead of a visualization, this widget uses a table — four decreasing values of h, showing f(a − h) and f(a + h) side by side. When the two columns converge, the limit exists. When they don't, it doesn't. Sometimes a table tells a story better than a chart.

When to add a new widget vs reuse

Reuse if: the existing widget does the same thing with different parameters, or you'd duplicate >50% of an existing widget's code.
Build new if: the concept needs a fundamentally different interaction (drag vs slider vs click), you'd bend an existing widget out of shape, or the new chapter has a unique visual metaphor.
For engineers The component-defined-inside-parent bug. Defining a sub-component inside a parent's render creates a new function reference per render, which React unmounts and remounts — losing input focus mid-typing. Always hoist helpers to module scope. We hit this once in RatioEquivalenceChecker and learned the hard way.
For PMs The Quiz widget is special — it appears in every chapter. To edit quiz questions for a chapter, open src/data/<slug>-questions.ts. It's a list of question objects with text, four options, the correct answer index, a hint, and an explanation.

From PDF to shipped chapter

Chapter Pipeline

Building a chapter from scratch would mean Claude reading the whole source PDF — slow and expensive. The pipeline splits the work in two: a cheap model extracts a brief, then Claude builds the page from the brief. Roughly 100× cheaper.

The big idea

Imagine handing a textbook chapter to a research assistant and asking for a one-page summary — just the rules, the key examples, the questions you'd want to test someone on. Then handing that summary to a different person who turns it into a website. That's the pipeline.

Stage 1: DeepSeek consumes the PDF text and emits a structured Markdown brief conforming to a strict schema. Stage 2: Claude reads only the brief (never the PDF) and generates the chapter page, widget components, and quiz TS file. The two-model split keeps Claude's input small — where it matters most for cost.

Two stages, three artefacts.

A typical chapter build runs in ~90 seconds and costs roughly two cents in API fees.

Stage 1 — DeepSeek extracts the brief

Driven by .claude/skills/create-chapter/scripts/make-brief.sh:

  1. Run pdftotext to convert PDF to plain text.
  2. Load the strict prompt from brief-prompt.txt.
  3. POST prompt + chapter text to DeepSeek's chat API.
  4. Save the response to src/data/briefs/<slug>-brief.md.
Why DeepSeek and not Claude here? DeepSeek's API is dramatically cheaper for input-heavy summarisation. NCERT chapters run 5,000–13,000 words; DeepSeek charges fractions of a cent. Claude would cost ~100× more.

What's in the brief

The prompt enforces a strict output schema:

  • YAML frontmatter (chapter number, title, route, read time).
  • One section block per major topic: concepts, worked examples, callout cards, widget idea, key terms.
  • Exactly 25 quiz questions as a JSON array with question, options, answer (0-indexed), hint, explanation.
What's stripped out. Exercise blocks — "Try these", "Figure it out", end-of-chapter problems. Valuable in a textbook, not what the brief is for. We want the teaching, not the homework.
For PMs Where the API key lives: in a file called .env.local at the project root. That file is gitignored — it never leaves your laptop. If you accidentally leak the key, get a new one from platform.deepseek.com.
For engineers The key is loaded by the script via set -a; . "$REPO_ROOT/.env.local"; set +a if DEEPSEEK_API_KEY isn't already in the env. .env* is in .gitignore.

Stage 2 — Claude builds the page

  1. Read the brief only (never the PDF).
  2. Extract the quiz JSON, write it as a typed TS file at src/data/<slug>-questions.ts.
  3. Build new widgets per the brief's widget ideas, reusing existing ones where possible.
  4. Write page.tsx, copying the structure of an existing chapter and filling fresh prose.
  5. Sync sidebars in previously-shipped chapters to link to the new one.

Then npm run build confirms everything compiles. A git branch and PR are opened.

If you only learn ten files

File Tour

The codebase has hundreds of files but ten carry most of the meaning. Read these and you can navigate the rest by analogy.

1. src/app/layout.tsx — the global wrapper

The outermost shell that wraps every page. Loads the two fonts. You'll rarely touch this.

The Next.js App Router root layout. Sets up <html> and <body>, loads Outfit + Inter via next/font/google, exposes them as CSS variables on <body>. Includes global metadata (title, description).

2. src/app/page.tsx — the homepage

The landing page at /. Lists three course tracks (NCERT Math, Engineering Math, Advanced Math). Grade 11 currently links to /read/grade-11/ch1; others show "coming soon".

3. src/app/read/grade-11/ch1/page.tsx — a typical chapter

The shape every chapter follows. Reading this one file gives you the mental template.

Open it once and skim. You'll see: a list of chapters at the top (used for the sidebar), then a big function that returns the visual layout — the navbar, the sidebar, the main content with sections and widgets and the quiz. Each chapter file is roughly the same shape with different prose and different widgets.

  1. "use client"; — opts in to client-side React.
  2. Imports — layout pieces, widgets, quiz pool.
  3. CHAPTERS array — the sidebar entries.
  4. Default export — returns JSX: Navbar, sticky Sidebar, <main> with sections.
  5. Each section uses the same numbered header pattern (giant Outfit-900 number + eyebrow + h2).

4. src/components/layout/WidgetShell.tsx — the universal wrapper

A 45-line component. Rounded card with header bar and body. Props: label, optional badge, children. Every widget wraps itself in this so the visual treatment is consistent across the whole site.

5. src/components/widgets/Quiz.tsx — used by every chapter

Takes pool (typed QuizQuestion[]) and count (default 10). Samples randomly, shows progress, supports hint-on-demand, marks correct/wrong, shows explanation, ends with score screen.

6. src/app/globals.css — the design tokens

The single source of truth for color, font, shadow, and border variables. Tailwind utilities and inline styles both read from these. To change the palette of the entire site, edit this one file.

7. src/data/grade-11-ch1-questions.ts — a typical quiz pool

The questions for Chapter 1's quiz. To edit a question, find it in this file and change the text. Each question has the prompt, four options, the index of the correct answer (0 means the first option), a hint, and an explanation that shows after the user answers. 

export const GRADE_11_CH1_QUESTIONS: QuizQuestion[] = [
  {
    question: "Which of the following is a set?",
    options: ["Tall people", "Vowels in English", "Good books", "Funny jokes"],
    answer: 1,
    hint: "A set must be well-defined.",
    explanation: "'Vowels in English' is unambiguous; the others are subjective."
  },
  // ...
];

8. src/data/briefs/grade-11-ch1-brief.md — a typical brief

The intermediate artefact from Stage 1 of the pipeline. Plain Markdown, strict schema. Read once by Claude during chapter authoring, then committed to the repo as a record. Never read at runtime by the website.

9. .claude/skills/create-chapter/SKILL.md — the workflow doc

Defines the create-chapter skill. Contains the full Stage 1 + Stage 2 workflow, a quality checklist, and what NOT to do. See the Chapter Pipeline section for the human-readable version.

10. .claude/skills/create-chapter/scripts/make-brief.sh — Stage 1 script

Bash script. Takes PDF path + slug, runs pdftotext, calls DeepSeek with the strict prompt, saves the result. ~110 lines total, mostly preflight checks and error messages. The actual API call is one curl command.
